Using JackedIN with AI agents

JackedIN is an SSH, Telnet and serial terminal for Windows, Linux and Raspberry Pi. The same program is a desktop window, a command line, a local API, and a stdio MCP server. Built-in profiles for Junos, Cisco IOS/NX-OS, Arista, Nokia, MikroTik and more.

Use it only on devices you own or are allowed to manage. Examples use 192.0.2.10 and router1. Keep passwords out of the command line; set JACKEDIN_PASSWORD or a credential reference instead.

Human approval before any change

Since JackedIN 1.2.2, MCP and the local API are read-only until a person approves a change:

  • Show-type commands (show, display, get, ping, traceroute) run freely.
  • A command that changes something waits until a person approves it in the window or, for jackedin headless, by typing allow on the terminal. A denial, or 60 seconds with no answer, means it is not sent.
  • The agent can never approve itself. There is no MCP tool or API field that grants approval.

This is a Pro feature, included with the 72-hour trial and with a license. jackedin exec and the window itself are not limited by it.

The problem agents hit

If you pipe a command into a raw SSH/serial session, end-of-file often ends the session while the device is still paging, or after it printed an error the agent never read. The agent moves on as if the change landed.

JackedIN is built so that does not happen.

Wait for the prompt, then read the complete output

jackedin exec reads the whole command list first, sends one command, and waits until the device prompt is back before it sends the next. It pages through --More--, ---(more)---, ---(more 100%)---, and similar markers, then returns the complete output. A stdin pipe on connect also waits for the prompt after each line; after stdin ends, it waits for the prompt that follows the last line, then exits.

There is no --terminator flag. The device prompt, and those pager markers, are how JackedIN knows a command has finished. --prompt REGEX replaces the prompt JackedIN detects. --vendor NAME forces a profile; omit it and the prompt or banner picks one.

Pacing, when a slow console needs it:

  • --line-delay MS — gap between lines (serial defaults to 100 ms if you omit it)
  • --char-delay MS — pause between characters
  • --wait-for-echo — wait until the device echoes a line before sending the next
  • !sleep 500 in a command list — wait 500 ms and send nothing
  • --timeout SEC — cap each wait; omit it and JackedIN waits as long as the device needs

The same pacing fields on the API and MCP are lineDelayMs, charDelayMs, and waitForEcho.

--dry-run prints the plan and connects to nothing. Prefer exec over piping into connect.

jackedin exec --host 192.0.2.10 --user admin --trust-host-key \
  --json --timeout 8 --cmd 'show version'

Coming from plink?

Plink is a fine, free SSH command-line tool. It is the wrong shape for an AI agent talking to a switch.

The PuTTY manual documents plink -m as reading a command file, and says that multi-line files are known not to work with certain embedded servers, such as Cisco routers. Plink can also take commands on stdin. In both cases it does not wait for the device prompt or page through --More--. The usual workaround is timeout, pause, or sleep between lines.

jackedin exec (and the MCP exec tool) sends one command, waits until the prompt on router1 is back, then sends the next. Optional --json reports whether each command succeeded. If you already have PuTTY sessions, JackedIN can import them.

Keep plink for Git and for a single remote command on a Unix server. Use JackedIN for device CLI, serial consoles, and agents. Since 1.2.2, jackedin plink accepts the common PuTTY plink flags, so a script can switch by changing one word, and agents get human approval before any change.

JSON output

--json and --output json are the same flag. JACKEDIN_JSON=1 matches them. On exec, each command is returned as structured data: command, ok, output, prompt, matched_error, timed_out, duration_ms. ok is false if any command, timeout, or verify check failed. fleet and inventory sync also accept JSON output.

On Windows, capture that output with jackedin.com, not jackedin.exe.

MCP server

jackedin mcp is a stdio MCP server for the local API. It dials 127.0.0.1 only. It is not a public URL.

  1. Install JackedIN 1.2.3 from the download section (72-hour full trial; a license is needed after that).
  2. Turn the local API on in Settings. It stays off until you do. It listens on 127.0.0.1 only (port 47321 unless you change it) and requires a Bearer token.
  3. Leave the window open, or run jackedin headless (the API must still be enabled).
  4. Point the client at the stdio command:
{
  "mcpServers": {
    "jackedin": {
      "command": "jackedin",
      "args": ["mcp"],
      "env": {
        "JACKEDIN_API_TOKEN": "paste-the-token-from-settings",
        "JACKEDIN_API_PORT": "47321"
      }
    }
  }
}

The packaged examples include this snippet for generic clients, Cursor, and Claude Desktop. The token is JACKEDIN_API_TOKEN if that variable is set, otherwise the token saved in Settings.

Tools: list_sessions, open_session, send_session, exec, send_break, read_session, close_session, wait_for_output, scan_ports, ping_host, trace_host, read_events. Prefer exec. exec and send_break do not require the automationApi setting; wait, scan, ping, trace, and events do. scan_ports tells the caller to only scan devices they are allowed to test.

The local API, off by default

The same work is available over HTTP on the local machine: POST /v1/exec, POST /v1/sessions/{id}/exec, and the other routes in the packaged docs/openapi.yaml. The listener is off until you enable it, bound to 127.0.0.1, and token-protected. Do not expose it on a network.

Safe use

  • Only connect to or scan devices you are allowed to test.
  • Do not put secrets in argv, MCP config files you will share, or logs. Use environment variables and the credential store.
  • Prefer --dry-run and show commands until you are sure of the plan.
  • A changed SSH host key is refused in the background; --trust-host-key accepts a new key, not a changed one.

Human approval before any change, in short

The same rule as the headline above, shipped in 1.2.2: in AI sessions, show-type commands run freely; a command that changes something waits for a person; the agent cannot approve its own change.
