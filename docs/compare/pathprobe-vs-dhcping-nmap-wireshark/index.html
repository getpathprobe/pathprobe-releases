PathProbe vs dhcping, nmap, and Wireshark

We built PathProbe. These four tools overlap on the word “DHCP” and then do different jobs. If you already have a capture, start with Wireshark. If you want to know whether a server answers at all, start with dhcping or an nmap script. PathProbe is for generating several lab clients — optionally VLAN-tagged — and keeping the pcapng.

Where the others win

dhcping

dhcping is small, old, and good at one thing: ask a DHCP server if it is still functioning. It can send DHCPREQUEST (default) or DHCPINFORM, wait for an answer, and then RELEASE. It typically needs root to bind port 68, and then it drops privileges. If that is the check you want, use it. Official author page: mavetju.org. Also packaged in Debian and Homebrew.

dhcping is the wrong shape for “give me five different clients, tag VLAN 20, and save a pcapng.”

nmap dhcp-discover and broadcast-dhcp-discover

If nmap is already in the toolkit, these scripts are the path of least resistance for discovery:

  • dhcp-discover
  • broadcast-dhcp-discover

They win at “what servers are out there, and what are they offering?” They are not a lease-holding, multi-client test bench, and they will not replace a structured lab capture.

Wireshark

Wireshark wins at analysis, every time. PathProbe does not decode better, filter better, or teach the protocol better. If you already have a pcap, you do not need PathProbe to read it. You may only need a display filter or the option decoder on this site, both of which run in your browser.

Where PathProbe is the better fit

  • You want several client identities from one computer, each with its own MAC, and a real DORA.
  • You want an 802.1Q tag on the test client, or (with Pro) QinQ.
  • You want the conversation saved as pcapng and then studied in Wireshark.
  • You want a tool that will not start a DHCP run unless you pass --authorized, because you should only test networks you own or are allowed to test.
